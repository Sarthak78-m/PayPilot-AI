--- QUERY 2: Constraints (PK, FK, CHECK, UNIQUE) ---

SELECT
  tc.constraint_name,
  tc.constraint_type,
  kcu.column_name,
  ccu.table_name AS foreign_table,
  ccu.column_name AS foreign_column,
  cc.check_clause
FROM information_schema.table_constraints tc
LEFT JOIN information_schema.key_column_usage kcu
  ON tc.constraint_name = kcu.constraint_name
  AND tc.table_schema = kcu.table_schema
LEFT JOIN information_schema.constraint_column_usage ccu
  ON tc.constraint_name = ccu.constraint_name
  AND tc.table_schema = ccu.table_schema
LEFT JOIN information_schema.check_constraints cc
  ON tc.constraint_name = cc.constraint_name
  AND tc.constraint_schema = cc.constraint_schema
WHERE tc.table_schema = 'public'
  AND tc.table_name = 'invoices';

2. INVOICE BUSINESS RULES
========================================================================

2a. Ownership
  - Every invoice belongs to exactly one authenticated user.
  - The user_id is set server-side from the verified Supabase session.
  - The client CANNOT assign, change, or spoof invoice ownership.
  - All queries filter by the authenticated user's ID.
  - RLS provides a second layer of enforcement at the database level.

2b. Amount
  - Must be a positive, finite number.
  - Maximum two decimal places (monetary precision).
  - Maximum value: 9,999,999,999.99 (fits numeric(12,2)).
  - Negative, zero, NaN, Infinity, and non-numeric values are rejected.
  - The database column (numeric(12,2)) is the authoritative precision.
  - JavaScript floating-point is acceptable for validation only;
    the database handles storage precision.

2c. Currency
  - Must be a valid ISO 4217 code from the supported set.
  - Currently supported: USD, EUR, GBP, CAD, AUD, INR.
  - Stored uppercase. Input is normalised to uppercase.
  - Extend the SUPPORTED_CURRENCIES set as the product grows.

2d. Customer details
  - customer_name: required, 1-200 characters after trimming.
  - customer_email: required, must pass email format validation.
  - description: required, 1-1000 characters after trimming.

2e. Due date
  - Must be a valid calendar date in YYYY-MM-DD format.
  - Invalid dates (e.g. Feb 30, month 13) are rejected.
  - Stored as a date type in the database (no timezone component).
  - Whether past due dates are allowed on creation is a product
    decision — currently permitted to support backdating drafts.

2f. Invoice status & transitions

  Valid statuses: draft, pending, paid, overdue, cancelled

  Transition matrix:

    From        | Allowed transitions to
    ------------|---------------------------
    draft       | pending, cancelled
    pending     | paid, overdue, cancelled
    overdue     | paid, cancelled
    paid        | (none — terminal state)
    cancelled   | (none — terminal state)

  Rules:
    - New invoices are created with status "draft".
    - The client cannot set the status during creation.
    - Status changes are validated against the transition matrix.
    - A PAID invoice cannot be reverted to any other status.
    - A CANCELLED invoice cannot be reactivated.
    - The "paid" transition will eventually require verified payment
      processing (PayPal Phase 4). During Phase 2 CRUD it is permitted
      via the API so the flow can be tested end-to-end.
    - The "overdue" transition may eventually be automated by a
      scheduled job that checks due_date < today for pending invoices.

2g. Deletion rules
  - Only "draft" invoices may be permanently deleted.
  - Invoices in any other status should be cancelled, not deleted.
  - This preserves the financial audit trail.
  - The DELETE endpoint will check the current status before acting.

3. VALIDATION IMPLEMENTATION
========================================================================

File created:
  backend/src/lib/invoices/validation.js

This file follows the exact same pattern as the existing
backend/src/lib/auth/validation.js:

  - Pure functions, no side effects, no database access.
  - Returns { valid: true, data } or { valid: false, errors }.
  - Trims and normalises inputs before validation.
  - Reusable across multiple API routes.

Exported functions:

  validateCreateInvoiceInput(input)
    Validates all required fields for creating a new invoice.
    Returns sanitised data: customer_name, customer_email,
    description, amount, currency, due_date.

  validateUpdateInvoiceInput(input)
    Validates only the fields provided for a partial update.
    Returns the sanitised subset of changed fields.
    Rejects requests with no valid fields.

  validateStatusTransition(currentStatus, newStatus)
    Validates whether a status change is permitted according
    to the transition matrix.
    Returns { valid: true } or { valid: false, error: "..." }.

  isValidUUID(value)
    Validates that a string is a properly formatted UUID.
    Used for validating route parameters (invoice ID).

Exported constants:

  SUPPORTED_CURRENCIES — Set of allowed ISO 4217 codes.
  VALID_STATUSES       — Set of allowed status values.
  STATUS_TRANSITIONS   — Map of allowed transitions per status.

No external dependencies were added.

4. PROPOSED API CONTRACTS
========================================================================

All endpoints require authentication. Every endpoint uses
getAuthenticatedUser() to verify the session. Unauthenticated
requests receive HTTP 401.

Response format follows project convention:
  Success: { "status": "ok", ... }
  Error:   { "status": "error", "message": "..." }


--- 4a. POST /api/invoices — Create Invoice ---

  Authentication: Required
  Content-Type: application/json

  Request body:
    {
      "customer_name":  "string (required, 1-200 chars)",
      "customer_email": "string (required, valid email)",
      "description":    "string (required, 1-1000 chars)",
      "amount":         number  (required, > 0, max 2 decimal places),
      "currency":       "string (required, ISO 4217, e.g. USD)",
      "due_date":       "string (required, YYYY-MM-DD)"
    }

  Server assigns:
    - id: generated UUID
    - user_id: from authenticated session
    - status: "draft"
    - created_at: now()
    - updated_at: now()

  The client CANNOT set: id, user_id, status, created_at, updated_at.

  Response (201):
    {
      "status": "ok",
      "data": {
        "id": "uuid",
        "user_id": "uuid",
        "customer_name": "...",
        "customer_email": "...",
        "description": "...",
        "amount": 150.00,
        "currency": "USD",
        "due_date": "2026-12-01",
        "status": "draft",
        "created_at": "2026-11-03T...",
        "updated_at": "2026-11-03T..."
      }
    }

  Error responses:
    400 — Invalid input (with errors object)
    401 — Not authenticated
    503 — Database unavailable


--- 4b. GET /api/invoices — List User's Invoices ---

  Authentication: Required

  Query parameters (all optional):
    status   — filter by status (e.g. ?status=pending)
    sort     — sort field (default: created_at)
    order    — asc or desc (default: desc)
    page     — page number (default: 1)
    limit    — items per page (default: 20, max: 100)

  Database operation:
    SELECT * FROM invoices
    WHERE user_id = <authenticated_user_id>
    [AND status = <status>]
    ORDER BY <sort> <order>
    LIMIT <limit> OFFSET <offset>

  RLS enforces user_id filtering at the database level.

  Response (200):
    {
      "status": "ok",
      "data": {
        "invoices": [ ... ],
        "pagination": {
          "page": 1,
          "limit": 20,
          "total": 42
        }
      }
    }

  Error responses:
    401 — Not authenticated
    503 — Database unavailable


--- 4c. GET /api/invoices/[id] — Retrieve Invoice ---

  Authentication: Required
  Route parameter: id (UUID)

  Database operation:
    SELECT * FROM invoices
    WHERE id = <id> AND user_id = <authenticated_user_id>

  RLS enforces ownership. If the invoice exists but belongs to
  another user, the query returns no rows (same as not found).
  This prevents information leakage about other users' invoices.

  Response (200):
    {
      "status": "ok",
      "data": { ... invoice object ... }
    }

  Error responses:
    400 — Invalid invoice ID format
    401 — Not authenticated
    404 — Invoice not found (or not owned by user)
    503 — Database unavailable


--- 4d. PATCH /api/invoices/[id] — Update Invoice ---

  Authentication: Required
  Content-Type: application/json
  Route parameter: id (UUID)

  Request body (all fields optional):
    {
      "customer_name":  "string",
      "customer_email": "string",
      "description":    "string",
      "amount":         number,
      "currency":       "string",
      "due_date":       "string",
      "status":         "string"
    }

  The client CANNOT change: id, user_id, created_at.
  updated_at is set server-side to now().

  Status changes:
    - If "status" is provided, validate against the transition matrix.
    - Reject invalid transitions with HTTP 409 and an explanation.
    - A PAID or CANCELLED invoice cannot be modified at all
      (any field change is rejected).

  Database operation:
    UPDATE invoices
    SET <changed_fields>, updated_at = now()
    WHERE id = <id> AND user_id = <authenticated_user_id>

  Response (200):
    {
      "status": "ok",
      "data": { ... updated invoice object ... }
    }

  Error responses:
    400 — Invalid input (with errors object)
    400 — No valid fields provided
    401 — Not authenticated
    404 — Invoice not found (or not owned by user)
    409 — Invalid status transition
    503 — Database unavailable


--- 4e. DELETE /api/invoices/[id] — Delete/Cancel Invoice ---

  Authentication: Required
  Route parameter: id (UUID)

  Business logic:
    - If status is "draft": permanently delete the row.
    - If status is "pending" or "overdue": set status to "cancelled"
      (soft delete — preserves audit trail).
    - If status is "paid" or "cancelled": reject with HTTP 409.

  Database operation (draft):
    DELETE FROM invoices
    WHERE id = <id> AND user_id = <authenticated_user_id>
      AND status = 'draft'

  Database operation (pending/overdue):
    UPDATE invoices
    SET status = 'cancelled', updated_at = now()
    WHERE id = <id> AND user_id = <authenticated_user_id>

  Response (200):
    {
      "status": "ok",
      "message": "Invoice deleted." | "Invoice cancelled."
    }

  Error responses:
    400 — Invalid invoice ID format
    401 — Not authenticated
    404 — Invoice not found (or not owned by user)
    409 — Cannot delete/cancel a paid or already cancelled invoice
    503 — Database unavailable

5. SECURITY CONSIDERATIONS
========================================================================

5a. Authentication
  - Every invoice endpoint calls getAuthenticatedUser().
  - If null is returned, the route responds with HTTP 401 immediately.
  - The authenticated user's ID (from Supabase session) is the ONLY
    source of user identity. Frontend-provided user IDs are ignored.

5b. Ownership enforcement (dual layer)
  - Application layer: all queries include WHERE user_id = <session_uid>.
  - Database layer: RLS policies restrict row access to the owning user.
  - Both layers must be active. Neither is sufficient alone.

5c. RLS requirements (to verify)
  The following RLS policies should exist on the invoices table:

    SELECT:  auth.uid() = user_id
    INSERT:  auth.uid() = user_id
    UPDATE:  auth.uid() = user_id
    DELETE:  auth.uid() = user_id

  These must be verified by running Query 4 from Section 1.

5d. No service-role bypass
  - Invoice operations use createSupabaseAuthClient() (cookie-based SSR
    client with the publishable key), NOT createSupabaseServerClient()
    (service role / secret key).
  - The service-role client bypasses RLS — it must never be used for
    invoice CRUD.

5e. Error message safety
  - No raw Supabase/PostgreSQL errors are returned to the client.
  - All error responses use hardcoded, safe messages.
  - Database constraint violation details are caught and mapped to
    user-friendly error messages.

5f. Input sanitisation
  - All string inputs are trimmed.
  - Email is lowercased.
  - Currency is uppercased.
  - Amount is validated as a finite positive number.
  - UUID route parameters are validated before querying.

6. SUGGESTED DATABASE IMPROVEMENTS
========================================================================

After verifying the current schema (Section 1 queries), the following
improvements may be needed. These should NOT be applied until the
current schema is inspected and discrepancies are identified.

6a. Index on user_id
  If not already present:
    CREATE INDEX idx_invoices_user_id ON invoices(user_id);

  This is critical for performance on the GET /api/invoices list
  endpoint, which filters by user_id on every request.

6b. Index on (user_id, status)
  For the status filter:
    CREATE INDEX idx_invoices_user_id_status ON invoices(user_id, status);

6c. CHECK constraint on status
  If not already present:
    ALTER TABLE invoices ADD CONSTRAINT chk_invoices_status
    CHECK (status IN ('draft', 'pending', 'paid', 'overdue', 'cancelled'));

6d. CHECK constraint on amount
  If not already present:
    ALTER TABLE invoices ADD CONSTRAINT chk_invoices_amount
    CHECK (amount > 0);

6e. updated_at trigger
  An automatic trigger to set updated_at = now() on every UPDATE:

    CREATE OR REPLACE FUNCTION update_updated_at_column()
    RETURNS TRIGGER AS $$
    BEGIN
      NEW.updated_at = now();
      RETURN NEW;
    END;
    $$ LANGUAGE plpgsql;

    CREATE TRIGGER set_invoices_updated_at
    BEFORE UPDATE ON invoices
    FOR EACH ROW
    EXECUTE FUNCTION update_updated_at_column();

Do NOT apply these until the current schema is confirmed.
