4. VALIDATION BEHAVIOR
-----------------------

  - customer_name: Required, string, 1 to 200 characters after trimming.
  - customer_email: Optional (nullable in DB). If provided, validated against email regex pattern.
  - description: Required, string, 1 to 1000 characters after trimming.
  - amount: Required, numeric, must be finite, strictly > 0, maximum 2 decimal places (cents precision), capped at 9,999,999,999.99 to respect NUMERIC(12,2).
  - currency: Required, checked against supported ISO 4217 currencies (USD, EUR, GBP, CAD, AUD, INR).
  - due_date: Optional (nullable in DB). If provided, validated as ISO YYYY-MM-DD calendar date with month/day boundary checking (e.g. Feb 31 rejected).
  - status: Client cannot set status on creation; always initialized server-side to "DRAFT" (matches PostgreSQL CHECK constraint).
  - id / user_id: Client cannot submit id or user_id; request rejected with 400 if client attempts to assign ownership.


5. AUTHENTICATION AND OWNERSHIP IMPLEMENTATION
------------------------------------------------

  - All three endpoints call `getAuthenticatedUser()` from `@/lib/auth/require-user.js`.
  - Unauthenticated requests immediately return HTTP 401 with standard error payload.
  - Ownership is derived strictly server-side: `user.id` is extracted from the verified Supabase Auth session token.
  - Dual-layer ownership enforcement:
      Layer 1 (Application): In queries, `eq("user_id", user.id)` is strictly appended.
      Layer 2 (Database RLS): Supabase client queries run with authenticated cookie context, enforcing PostgreSQL row security.
  - Cross-user invoice access: When User B queries an invoice owned by User A, the query returns 0 rows, resulting in HTTP 404 (not exposing whether the invoice even exists).


6. RLS USAGE
-------------

  - Routes use `createSupabaseAuthClient()` from `@/lib/supabase/server.js`.
  - The client forwards auth session cookies and uses `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`.
  - No service-role (`SUPABASE_SECRET_KEY`) bypass is introduced or used in any invoice endpoint.
  - RLS policies on `public.invoices` (`auth.uid() = user_id`) remain fully active and enforced.
